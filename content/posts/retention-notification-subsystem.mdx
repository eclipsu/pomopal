Pomopal is a focus app. Focus apps die the quiet death of “I’ll start again Monday.”

Streaks help — but only if you protect them on the day someone’s about to lose one. That means messages that feel personal, arrive at the right local hour, and never accidentally fire twice. We built that as a **first-class notification subsystem**, not a pile of `if` statements next to the timer.

This is how it works.

## What “good” means for us

We wanted four things:

1. **Local time, not UTC arrogance** — 9pm for a user in Tokyo is not 9pm in Chicago.
2. **Content without deploys** — ops should ship copy and images from an admin panel.
3. **Prefer saying nothing over saying the wrong thing** — eligibility is a hard gate.
4. **Dual delivery with one preference model** — in-app + email, same intent toggles.

No notification SaaS. No Redis queue on this path. NestJS, Postgres, S3, and SMTP.

## The shape of the system

```text
Triggers                         Pipeline                        Delivery
────────                         ────────                        ────────
Hourly cron (user TZ)    →     pick template + render     →    notifications row
Pomodoro milestones      →     preference gates           →    SMTP (CID image)
Admin broadcast / revive →     unique dedupe_key          →    bell UI (poll)
```

Types we care about in production: `streak_at_risk`, `streak_milestone`, `daily_nudge`, `comeback`, `announcement`.

## Timezone cron — and why we jitter

Every hour, a scheduler walks users and evaluates **their** local clock: streak risk at 21:00 / 23:00, comebacks at 10:00, daily nudges at the user’s empirical focus hour (mode of completed-session hours, else 17:00).

Then we smear sends with a deterministic delay derived from the user id — soft thundering-herd protection without introducing a job queue:

```ts
const userSeed = parseInt(user.id.replace(/-/g, '').slice(0, 8), 16);
const delayMs = (userSeed % 59) * 60 * 1000; // 0–58 min

if (STREAK_NUDGE_HOURS.has(hour)) {
  setTimeout(() => {
    void this.maybeStreakAtRisk(user.id, user.email, tz, today, hour);
  }, delayMs);
}
```

Streak-at-risk itself is product-shaped: only when the streak is live, the user isn’t active today, and they’re still inside a short grace window — with a distinct “last chance” send at 11pm on the final grace day. Dedupe keys encode that (`today:early` vs `today:last`) so retries can’t double-text someone who’s already been warned.

## Templates that refuse to lie

Admins author templates with `{{username}}`, `{{streak}}`, `{{graceDaysRemaining}}`, and friends. Eligibility lives in jsonb — a small fixed rule set (`minStreak`, `requiresLastChance`, `minDaysAway`, …), not a free-form DSL. That’s intentional: ops can reason about it; eng can keep it correct.

```ts
if (bool('requiresLastChance') === true && !isLastChance) return false;
if (bool('requiresEarlyNudge') === true && isLastChance) return false;
```

Among eligible active templates we pick uniformly at random — lightweight A/B without another service. The important product rule sits one layer up:

- **No templates configured** → witty hardcoded fallbacks.
- **Templates exist but none match this user** → **skip the send**.

```ts
if (template) {
  title = renderTemplate(template.title, params.context);
  body = renderTemplate(template.body, params.context);
} else if (templatesConfigured) {
  // Prefer silence over the wrong copy.
  return null;
} else {
  const copy = params.fallback();
  title = copy.title;
  body = copy.body;
}
```

That skip rule is the kind of boring decision that quietly earns trust.

## Idempotency is not optional

Every notification carries a unique `dedupe_key` (`streak_at_risk:user:day:early`, `announcement:runId:user`, milestone keys, …). We check first, then insert, and still catch Postgres unique violations — because two cron workers (or a retry) will eventually race:

```ts
async createIfNew(params: CreateParams): Promise<Notification | null> {
  const existing = await this.notificationRepo.findOne({
    where: { dedupe_key: params.dedupeKey },
  });
  if (existing) return null;

  try {
    return await this.notificationRepo.save(/* ... */);
  } catch (err) {
    if (isDuplicateKeyError(err)) return null;
    throw err;
  }
}
```

## Preferences map to intent, not channels

Users don’t get a 12-toggle email matrix. They get intent:

| Toggle | Gates |
|--------|--------|
| Streak updates | milestones |
| Streak nudges | at-risk + daily nudge |
| Inactive reminders | comeback |
| Product announcements | broadcasts |

In-app and email share those gates. Missing prefs default **on** — you opt into the product by using it; you opt out when it gets noisy.

Announcements fan out in batches (insert in-app, then paced email) so a launch post doesn’t melt SMTP.

## Email is craft, not an afterthought

Template images live on S3. For email we don’t blindly paste a WebP URL and pray. We pull bytes, convert WebP/GIF → PNG with `sharp` for client compatibility, and embed as a **CID** attachment inside a table-based HTML card. Gmail is a harsh reviewer; we write for Gmail.

## What I’d tell a hiring manager

This wasn’t “we hooked up a vendor.” It’s a retention loop treated as product surface:

- timezone-native scheduling with personalized send hours  
- ops-editable copy with eligibility that fails closed  
- dual delivery, preference taxonomy, and race-safe dedupe  
- email that survives real clients  

The next upgrades are obvious and honest: a durable queue for jittered work (restarts currently drop pending `setTimeout`s), push instead of 60s polling for the bell, and retiring a couple of half-lit type paths. Scale problems we’re happy to grow into.

Until then — if your streak is about to die at 11pm local, Pomopal will try to say the right thing once. Not twice. Not in the wrong timezone. Not with last week’s template.
